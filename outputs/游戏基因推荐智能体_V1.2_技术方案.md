## 0. 文档信息

- 项目：SYE 6602 - Game Gene Agent
- 路线：Another Tool Route
- 方案版本：V1.2（初步可展示版修订稿）
- 设计基线：原V1技术方案、V1.1技术方案、初步计划及V1.1设计评审结论

### 0.1 本轮修订摘要

- 将V1.1的Jaccard双轨算法改为用户熟悉类型覆盖率，并把阈值改为校准后冻结的配置项；
- 明确V1.2核心表层类型只来自appdetails genres，SteamSpy和HTML标签仅可作为非核心增强；
- 将Steam导入拆成“纯问卷画像—授权预览—确认提交”三步；
- 明确完整清除Steam数据时必须处理当前画像、历史版本和预览缓存；
- 将证据等级固定为A/B/C/Rejected，引文匹配失败必须Rejected；
- 为等级0、未知平台／语言／社交模式、价格和表层genres规定确定处理方式；
- 简化ExplanationFacts资源检查，修正fallback指标分母；
- 固定请求规范化与SHA-256哈希语义；
- 增加V1.1到V1.2的数据重建／显式迁移策略；
- 将交付拆为P0、P1、P2，避免开发者界面和细粒度数据管理阻塞课程核心闭环。

## 1. V1.2目标

V1.2要交付一个可以本地运行、可以通过HTTP调用、能够保存和回看结果的Steam游戏推荐系统。用户通过问卷建立九维游戏基因画像，可选择授权导入公开Steam游戏库。系统在经过证据核验的游戏目录中进行硬过滤与相似度计算，再输出：

1. **同类轨（same-track）**：表层类型与用户熟悉类型接近，且深层游戏基因匹配；
2. **其他轨（cross-track）**：表层类型不同，但深层游戏基因匹配；
3. **最接近候选（closest-only）**：候选本身满足目录与证据准入要求，但没有达到正式推荐匹配门槛；
4. **明确无匹配（no-match）**：没有足够匹配且证据充分的候选，不允许模型强行生成答案。

每条正式推荐必须包含匹配基因、证据原句、证据等级、匹配分数和可能的劝退点。匹配基因包括共同吸引点、共同规避点和强度相容，不再只识别用户与游戏均为高等级的维度。

推荐运行必须持久化，后续能够按`run_id`原样读取。使用模板fallback时必须明确告知用户；模板所需信息不足时，不得强行生成解释。

系统首先提供可导出的结构化诊断JSON；P1/P2可增加本地**开发者模式**界面，用于展示错误所在工作流、模块、操作、数据记录、重试、fallback及相关文件位置。任何诊断输出都不允许泄露API Key或未脱敏个人Steam信息。

### 2.4 数据规模分级

- **真实试验**：先用5款真实游戏验证默认模型的结构输出、引文核验、耗时和费用；
- **V1-MVP**：至少30款真实游戏跑通完整目录流水线，用于验证闭环和初步校准，并记录每款的`verified`、`partial`或`failed`状态；
- **V1-Final**：种子池约300款真实Steam游戏，目标为至少200款达到`verified`；
- **时间不足时的降级交付**：优先保证至少100款高质量真实目录记录，而不是通过放宽证据或verified标准凑数量；
- **演示要求**：当前已完成目录中应有足够的`verified`游戏支持至少一个固定、可复现测试画像的双轨推荐演示。

“30款完成流水线”不等于“30款必须全部verified”；“200款verified”是V1-Final质量目标，也不能成为降低证据标准的理由。证据不足的游戏应保留为`partial`，采集或处理失败的游戏应保留失败原因。未达到目标时应报告实际数量、通过率和失败原因，不得删除失败记录或修改门槛以追求数字。

上述数量描述的是课程版本预先构建和缓存的真实目录规模，不是产品永久的推荐边界。推荐器读取当前所有`verified`记录；后续可通过相同流水线继续增加AppID，或扩展为运行时动态候选发现。

## 4. 三个工作流与诊断能力

### 4.1 工作流一：用户画像构建与Steam导入

#### 输入

第一步使用`POST /api/profiles`建立纯问卷画像：

```json
{
  "display_name": "Alice",
  "answers": {"q1": ["a"], "q2": ["c"]},
  "filters": {
    "platforms": ["windows"],
    "social_modes": ["single"],
    "max_price_cents": 3000,
    "price_currency": "usd",
    "required_language": "english",
    "exclude_owned": true
  },
  "steam_id_or_url": null,
  "steam_import_consent": false
}
```

Steam导入采用两阶段接口，不能在一次创建画像请求中同时完成“读取、预览、用户选择和融合”：

1. `POST /api/profiles/{id}/steam-import/preview`：在用户明确同意后读取公开Steam游戏库，返回预览，不修改画像；
2. `PUT /api/profiles/{id}/steam-import/selection`：P0提交批量导入策略并生成新的画像revision；P1可在同一请求中增加逐游戏覆盖项；
3. `DELETE /api/profiles/{id}/steam-import`：清除本地Steam导入数据并根据已保存问卷重建纯问卷画像。

#### 问卷映射要求

在画像模块完成前，必须提供独立问卷映射文档，至少包含：

- 稳定的题目ID和实际题目文本；
- 每题对应的基因维度；
- 每个选项到`target`的确定映射；
- `weight`的产生规则；
- 第10道强制选择题的职责；
- 多题影响同一维度时的合并规则；
- 缺失、非法答案和边界值处理；
- 每组测试答案的预期画像。

V1.2以本技术方案的九维0—4分模型为唯一实现基线，原始双极九维表只作为历史设计参考，不与当前问卷混用。

#### 执行顺序

1. Pydantic校验请求形状；
2. 业务校验昵称、问卷完整性、选项合法性、熟悉标签、价格和币种；
3. 在任何Steam或模型调用之前一次性返回全部输入问题；
4. 按公开问卷映射规则计算九维`target`和`weight`；
5. 保存纯问卷画像至`profiles/<profile_id>.json`，更新时保留历史版本；
6. 用户主动进入Steam导入流程后，检查`steam_import_consent`；未同意时接口调用次数必须为0；
7. 预览接口解析SteamID并读取公开游戏库，只返回暂存预览，不修改画像；
8. 用户确认后，P0按批量策略记录“所有符合条件的游戏参与画像”和“所有已拥有游戏从推荐中排除”；P1允许提交逐游戏覆盖项；
9. 默认只对游玩时间不少于60分钟、存在于已验证目录且被用户允许参与的游戏进行画像融合；
10. 保存融合前后画像及每款游戏的贡献，并产生新的画像revision；
11. Steam导入失败时保留纯问卷画像，并显示warning，不让整个流程失败。

#### Steam数据控制

Gradio提供以下简单控件：

- 默认未勾选的“同意读取公开Steam游戏库”复选框；
- “导入Steam游戏库”按钮；
- 导入后的游戏表格，显示名称、AppID、游戏时长、是否满足融合条件；
- **P0**：“确认导入全部符合条件游戏”按钮，以及“排除全部已拥有游戏”选项；
- **P1**：逐游戏“纳入画像”和“推荐时排除”复选框；
- **P1**：“保存逐游戏设置”“移除所选本地记录”和“清除Steam导入数据”按钮。

“删除”只删除本地导入记录及其画像贡献，不修改用户的Steam线上游戏库。清除导入数据后，系统根据已保存问卷重新计算纯问卷画像。

“清除Steam导入数据”采用隐私清理语义，而不是只停用当前画像：

- 清除当前画像中的SteamID、owned_appids、导入控制和融合贡献；
- 清除Steam导入预览缓存；
- 对画像历史版本中的SteamID、游戏库和融合贡献进行删除或不可逆脱敏；
- 推荐运行可以保留，但不得包含原始SteamID、完整游戏库或导入预览；
- 清理操作是“历史只增不改”规则的明确隐私例外，并生成一条不含个人数据的purge audit记录。

如果实现阶段不准备清理历史数据，则界面不得称为“清除数据”，只能称为“在当前画像中停用Steam融合”，并明确告知历史记录仍保留。V1.2默认采用前述完整隐私清理语义。

#### 输出

`UserProfile`包含九维偏好、权重、熟悉标签、硬过滤条件、已拥有／排除AppID、Steam授权状态、导入游戏控制状态、画像来源、融合贡献和稳定的`profile_id`。

### 4.2 工作流二：游戏目录与证据流水线

#### 触发方式

离线CLI批处理：

```bash
uv run gamegene catalog build --appids data/seed/appids.csv --limit 5
```

先完成单模型5款试验，再运行30款真实校准。30款结果未达到演示要求时，优先修复流水线，不直接扩到100款或300款。

#### 数据来源与采集要求

核心来源为：

- Steam商店信息；
- Steam用户评测；
- Steam appdetails中的官方genres和categories。

SteamSpy和Steam商店HTML标签抓取不作为当前核心依赖。V1.2的双轨划分只使用appdetails中可稳定取得并能映射到固定taxonomy的genres；categories用于平台、单人／多人／合作等能力判断，不与genres混成同一个表层类型集合。可选标签增强只能作为补充，失败不得影响核心目录或双轨划分。

采集器需要处理无效AppID、下架、地区差异、年龄验证、免费游戏、无价格、评测语言混杂、429、超时和局部失败。

字段规范化要求：

- 平台使用统一枚举；
- 社交模式通过固定类别映射表生成，未知时显式保存未知；
- 语言过滤明确区分界面、字幕和语音，当前至少记录判定口径；
- 价格保存币种、地区、原价、现价、折扣和获取时间；
- 每个来源保存快照和获取时间；
- 可选标签增强失败不应删除已保存的商店或评测数据；
- 新一次失败不得覆盖旧的`verified`记录。

#### 执行顺序

1. 从CSV读取AppID；
2. 按主机限速访问核心Steam数据源；
3. 保存`data/raw/<appid>/`原始响应快照；
4. 规范化名称、描述、genres、categories、平台、语言、社交模式和价格；
5. 先保存`pending`记录；
6. 构建最多24k字符的证据passages，24k是上限而非填充目标；
7. 调用默认真实模型返回九维结构化标注、引文和来源段落编号；
8. 用纯代码检查引文是否出现在缓存来源中，并保存匹配结果；
9. 对证据分为A/B/C或拒绝；
10. 没有A/B级证据的维度必须为`null`；
11. 已知基因不少于5个且其他准入条件满足时写为`verified`，否则写为`partial`；
12. 失败写入批处理报告；已有`verified`记录不能被一次失败覆盖。

#### 证据分级与verified语义

- **A级**：官方商店描述或官方说明中的引文逐字匹配，并能够支持对应机制；
- **B级**：至少两条相互独立的用户评测对同一机制给出一致支持，展示引文逐字匹配其中一条来源；
- **C级**：只有一条用户评测、仅为模糊匹配或语义支持较弱，只保存供人工复核，不用于正式推荐解释；
- **Rejected**：引文匹配失败、来源缺失、引文与所标维度无关或无法支持对应机制。

只有A/B级证据可以支撑非空基因并进入正式推荐。C级证据可以保存在候选记录中，但对应基因必须为`null`；Rejected证据只进入诊断或批处理报告，不进入正式目录事实。

引文存在性核验只证明原文可追溯，不自动证明分数正确。`verified`表示记录结构有效、引文可追溯、至少5个维度满足目录准入条件，不表示九维评分已经得到客观验证。

人工校准重点检查引文是否支持维度和分数，并覆盖：

- 所有最终展示推荐涉及的维度和证据；
- 每款校准游戏至少2个非空维度，不足2个则检查全部非空维度；
- 所有异常高分、低质量证据和争议记录。

证据记录增加`semantic_review_status = pending / approved / rejected`。冻结演示目录前，所有会出现在推荐卡片中的匹配点和劝退点必须为`approved`。其余自动标注维度可以保持`pending`，但不得在界面中被表述为已人工验证。

等级0同样需要证据。对于“共同规避点”，只有官方文本明确说明某机制不存在，或固定类别映射满足预先书面定义的否定规则时，才能赋值0；“页面没有提到”只能记为`null`，不能作为低—低匹配证据。

#### 状态机

```text
new -> pending -> verified
              -> partial
              -> failed
```

只有`verified`游戏可以进入正式推荐候选池。

### 4.3 工作流三：推荐与历史

#### 输入

`POST /api/recommendations`

```json
{
  "profile_id": "p-1a2b3c4d",
  "mode": "both",
  "top_k": 3,
  "request_id": "demo-normal-001"
}
```

`mode`支持`both`、`same_track`、`cross_track`。保留普通字符串而不是枚举，以便课程测试能够发送未知值，证明Router的no-matching-path分支实际生效。

#### 执行顺序

```text
validate -> route -> load profile -> hard filters -> score
         -> assign tracks -> evidence gate -> build explanation facts
         -> explain / fallback -> save
```

#### 主要分支

| 分支 | 条件 | 结果 |
|---|---|---|
| A | `request_id`已存在且规范化请求哈希相同 | 返回原来的运行，不重复调用模型 |
| A2 | `request_id`已存在但请求内容不同 | HTTP 409，不覆盖旧运行 |
| B | `profile_id`不存在 | HTTP 404，不进入推荐 |
| C | mode不受支持 | 保存`no_match`，trace=`no_matching_path` |
| D | 硬过滤后候选为0 | 保存`no_match`，记录每类剔除数量 |
| E | 至少有一款通过分数和证据门槛 | 保存`ok`，输出指定轨道Top K |
| F | 无正式推荐，但证据合格候选最高分不低于0.55 | 保存`closest_only`并解释有效匹配点与差异 |
| G | 最高分低于0.55，或候选缺乏必要证据 | 保存`no_match`，不调用解释模型 |
| H | 可保存的内部业务错误 | 保存`error`与结构化错误信息 |
| H2 | 存储本身不可用 | 返回结构化HTTP错误并写脱敏日志，不承诺生成新运行文件 |

`closest_only`不得用于绕过证据门槛。证据不足的候选只能进入`no_match`或保留为目录`partial`，不能生成基因推荐理由。

### 4.4 结构化诊断与可选开发者模式

P0要求三个工作流都能输出结构化、可导出且脱敏的诊断JSON。P1/P2可增加开发者模式界面；该界面默认关闭，可通过Gradio复选框或本地配置`GAMEGENE_DEV_MODE=true`开启。

普通模式只显示人类可读的warning、fallback或error。开发者模式额外显示：

- `error_id`、`request_id`、`run_id`；
- 工作流、模块和具体操作；
- 相关AppID或`profile_id`；
- 错误代码、脱敏消息和上游状态；
- 是否可重试及已尝试次数；
- fallback触发原因、资源检查和渲染状态；
- 每个trace步骤的成功状态与耗时；
- 相关快照、目录、运行和报告文件位置；
- 本地折叠面板中的脱敏traceback。

开发者模式用于定位和指导代码修改，不自动修改系统代码，也不关闭任何敏感信息脱敏规则。

## 5. 九维游戏基因

V1.2沿用原V1技术方案的九个维度，统一使用0—4等级；缺少证据时必须为`null`，不能用0代替未知。

| ID | 中文 | 说明 |
|---|---|---|
| `challenge` | 操作挑战 | 成功对练习、精度和克服失败的依赖 |
| `strategy` | 策略深度 | 对计划、优化和权衡的依赖 |
| `pace` | 节奏强度 | 实时压力和单位时间行动密度 |
| `progression` | 成长积累 | 等级、装备、解锁和长期积累的重要性 |
| `exploration` | 探索发现 | 未知区域、秘密和机制发现的重要性 |
| `creation` | 创造表达 | 建造、设计、自定义和玩家表达空间 |
| `narrative` | 叙事 | 剧情、角色和对话对体验的驱动力 |
| `immersion` | 世界沉浸 | 氛围、世界感和代入感的重要性 |
| `social` | 社交依赖 | 核心体验对合作或竞争玩家的依赖 |

### 等级含义

- 0：不存在；
- 1：次要存在；
- 2：有实际作用但不是主要吸引点；
- 3：主要吸引点之一；
- 4：游戏围绕该维度构建；
- `null`：没有足够证据，未知。

每个非空维度必须至少绑定一条通过原文匹配的A/B级证据。评分是否得到充分语义支持由校准检查评估，不能只依赖字符串匹配。

## 6. 推荐算法

### 6.1 硬过滤顺序

候选游戏按固定顺序检查，命中首个原因就剔除并计数：

1. 状态不是`verified`；
2. 已拥有、被用户设置为推荐排除或位于排除AppID集合；
3. 命中排除标签；
4. 平台不匹配；
5. 社交模式不匹配；
6. 语言不匹配；
7. 已知价格超过上限；
8. 已知基因少于5个，无法稳定评分；
9. 缺少可用于双轨划分的规范化表层genres，记录`missing_surface_labels`。

价格比较必须使用相同币种和地区语境。过滤所需字段的缺失处理固定如下：

| 字段 | 用户未设置相关硬过滤 | 用户明确设置相关硬过滤 |
|---|---|---|
| 平台 | 放行 | 未知或无交集时剔除，记录`platform_unknown`或`platform` |
| 社交模式 | 放行 | 未知或不匹配时剔除，记录`social_mode_unknown`或`social_mode` |
| 语言 | 放行 | 未知或不匹配时剔除，记录`language_unknown`或`language` |
| 价格 | 放行 | 价格未知、币种不同、地区不一致或数据过期时剔除，记录`price_unverifiable`；明确超过上限时记录`price` |
| 表层genres | 不适用 | 缺失时不得进入双轨结果，记录`missing_surface_labels` |

V1.2对用户明确设置的硬条件采用fail-closed，避免把无法确认的候选当作已满足条件。界面同时显示各类未知字段造成的剔除数量。

### 6.2 相似度

设用户和游戏共同已知、可以参与计算的基因集合为`K`：

```text
similarity = 1 - sum(w_i * abs(target_i - level_i))
                 / (4 * sum(w_i)), i in K

coverage = sum(w_i, i in K) / sum(w_i, all genes)

score = similarity * (0.7 + 0.3 * coverage)
```

覆盖率用于惩罚只有少量已知基因的游戏，避免“信息少反而分数高”。实现必须处理`K`为空、分母为0、非有限数值和非法权重等边界情况。

当前公式及0.7／0.3系数保持原V1设置，其参数可信度校准列入后续工作。

### 6.3 表层标签标准化

用户熟悉标签及其权重记为`U`，候选游戏规范化后的核心genres集合记为`G`。两者必须使用同一份固定taxonomy；Steam categories不进入`G`。

标准化规则：

- 去除首尾空白并统一大小写；
- 使用同一套英文canonical genre ID和固定问卷选项；
- 去除重复项；
- 通过固定别名表处理已知同义标签；
- 不使用LLM临时扩展或猜测标签。

用户至少选择一个熟悉标签。候选游戏必须具有可用于轨道划分的规范化genres；字段缺失不能被直接解释为“跨类型”。问卷映射文档必须同时提供canonical genre列表和别名表，不能只在代码中隐式维护。

### 6.4 双轨划分

V1.2使用“用户熟悉类型覆盖率”，避免用户标签很少、游戏标签很多时Jaccard分母系统性偏大：

```text
surface_overlap =
sum(user_tag_weight[t] for t in U ∩ G)
/
sum(user_tag_weight[t] for t in U)
```

- `surface_overlap >= TRACK_OVERLAP`：同类轨；
- `surface_overlap < TRACK_OVERLAP`：其他轨；
- 候选缺少可用表层genres：不自动分配轨道，记录`missing_surface_labels`，不得伪装成其他轨。

类型标签只决定轨道，不参与九维基因相似度。某一轨没有合格候选时允许为空，不通过降低证据或匹配门槛强行补足数量。

`TRACK_OVERLAP`默认实验值为0.50，不作为已验证结论。5款试验后可以预调，30款校准后必须冻结最终值、测试用例和修改理由；演示期间不得临时调整。

### 6.5 匹配基因

某维度成为匹配基因，必须同时满足：

```text
target不为null
level不为null
abs(target - level) <= 1
该维度至少有一条A/B级证据
```

匹配基因分为：

| 类型 | 含义 | 示例 |
|---|---|---|
| 共同吸引点 | 用户与游戏在该维度都较高 | 用户策略4，游戏策略4 |
| 共同规避点 | 用户与游戏在该维度都较低 | 用户社交0，游戏社交0 |
| 强度相容 | 双方接近，但不属于明显高低两端 | 用户叙事2，游戏叙事3 |

推荐卡片使用“匹配点”作为总称，并展示具体类型。多个匹配基因用于解释时，依次考虑用户权重、距离、证据等级和固定维度ID排序，保证可复现。

差值较大的已知维度可作为劝退点；游戏侧机制描述必须有证据，不允许只凭模型常识生成。

### 6.6 推荐门槛

正式推荐必须同时满足：

- `score >= 0.72`；
- 至少存在一个匹配基因；
- 至少一个匹配基因具有A/B级证据；
- 候选已经通过全部硬过滤和目录准入。

最终排序固定为`(score降序, appid升序)`，保证相同输入可复现。

`closest_only`只从证据合格的候选中产生，用于表达“相对接近但未达到正式推荐门槛”。`no_match`用于证据不足、无有效匹配解释、硬过滤后为空或最高分低于0.55等情况。

当前0.72、0.55及置信度定义与参数可信度校准列入后续工作，不宣称这些初始值已经得到统计验证。

## 7. LLM与fallback方案

### 7.1 V1.2默认方案

- 主要接入：OpenRouter；
- 定位：默认模型网关，不是课程强制要求；
- SDK：OpenAI Python SDK；
- 默认模型：先使用组内Key实际可调用的一款模型；
- 备选：其他OpenRouter模型、GLM、Gemini、DeepSeek或提供商直接API；
- 统一接口：`LLMClient.complete_json(system, user, schema)`。

先以5款真实游戏测试单模型的首次结构校验通过率、引文核验通过率、耗时和费用，将结果写入`docs/calibration.md`。多模型比较列入后续计划。

### 7.2 LLM只负责两件事

1. 根据已有passages提出九维基因标注与引文；
2. 根据已选出的匹配基因、差异和证据生成自然语言解释。

LLM不负责输入校验、硬过滤、打分、排序、双轨划分或是否推荐的最终决定。

### 7.3 模型输出安全链

```text
LLM raw text
 -> remove code fences
 -> json.loads
 -> Pydantic validation
 -> business-rule validation
 -> bounded retry
 -> annotation: null / partial / failed
 -> explanation: gated deterministic fallback
```

模型标注中的引文在原始快照中找不到，则该维度写为未知；解释引用了未提供的基因或`evidence_id`，则该次LLM解释判定为业务校验失败。

### 7.4 标注失败与解释失败必须分开

| 阶段 | LLM失败后的允许行为 |
|---|---|
| 游戏基因标注 | 有限重试；无依据维度置为null；游戏进入partial或failed；保留旧verified记录 |
| 推荐自然语言解释 | 有限重试；最低资源检查；满足条件时使用模板并明确告知用户 |

模板不得生成九维基因、游戏机制或证据。它只能重述推荐阶段已经确定的结构化事实。

### 7.5 ExplanationFacts

LLM解释和模板fallback必须使用同一个冻结的`ExplanationFacts`对象，禁止分别临时读取不同数据。对象使用Pydantic frozen model或等价不可变结构，在调用LLM前只进行一次完整业务校验；LLM失败后直接复用同一对象渲染模板。

最低结构包括：

```text
run_status
game.appid
game.name
track
score
comparisons[]
matching_genes[]
mismatches[]
evidence[]
template_version
```

每个比较项至少包含：

```text
dimension_id
user_target
game_level
difference
comparison_type
```

每条证据至少包含：

```text
evidence_id
quote
grade
source_reference
related_dimension
```

### 7.6 fallback最低资源列表

| 资源 | 最低要求 | 缺失处理 |
|---|---|---|
| 推荐状态 | 明确为`ok`或`closest_only` | 不生成推荐解释 |
| 游戏身份 | AppID和名称存在 | 阻止fallback |
| 所属轨道 | same-track或cross-track明确 | 阻止fallback |
| 匹配分 | 模板展示分数时必须为有限数值 | 阻止包含分数的完整模板 |
| 比较信息 | 至少一个完整合法的维度比较项 | 阻止fallback |
| 正式推荐匹配点 | `ok`至少有一个匹配基因 | 阻止正式推荐解释fallback |
| 游戏机制证据 | 被陈述的游戏基因具有A/B级证据 | 删除该陈述；无有效陈述则阻止fallback |
| 引文 | 证据ID、原句和来源引用完整 | 对应证据不可用于模板 |
| 模板 | 模板存在、版本明确且可渲染 | 记为fallback自身失败 |

对于`closest_only`，必须至少有一个完整比较项，并能够说明至少一个有效匹配点或差异点。不能只凭分数生成“最适合你”等超出现有事实的表述。

价格、知名度、额外表层劝退点、第二条或第三条证据属于可选资源。缺失时省略对应句子，不阻塞整个fallback。

### 7.7 fallback执行流程

```text
生成ExplanationFacts
        |
        v
最低资源检查并冻结对象
        |
        +-- 信息不足
        |     -> 不调用LLM和fallback
        |     -> explanation_status = insufficient_data
        |     -> 记录缺失字段
        |
        +-- 信息完整
              -> 调用LLM
                    |
                    +-- 成功且校验通过
                    |     -> explanation_source = llm
                    |     -> fallback_status = not_needed
                    |
                    +-- 失败或校验不通过
                          -> 有限重试
                          -> 直接复用已经校验并冻结的ExplanationFacts
                          -> 渲染模板
                                +-- 成功：rendered并告知用户
                                +-- 异常：render_failed
```

如果实现需要跨进程传递或重新反序列化ExplanationFacts，则允许对“序列化后重新读取的副本”再次校验；不得把重复校验同一不可变内存对象作为正常流程。`blocked_missing_data`只用于首次资源检查失败，或反序列化副本确实缺失必要字段的情况。

### 7.8 状态与用户提示

`llm_status`至少支持：

```text
not_called / success / timeout / connection_error / rate_limited
upstream_error / invalid_json / schema_invalid / business_validation_failed
```

`fallback_status`至少支持：

```text
not_needed / not_attempted / rendered / blocked_missing_data / render_failed
```

调用LLM前资源不足时使用`fallback_status=not_attempted`与`explanation_status=insufficient_data`，避免把“没有尝试fallback”误记为“fallback失败”。

同时记录：

- `fallback_missing_fields`；
- `fallback_resource_status`；
- `fallback_trigger_reason`；
- `template_version`；
- LLM实际调用与重试次数。

普通用户提示规则：

| 情况 | 用户提示 |
|---|---|
| LLM失败，模板成功 | “AI解释暂时不可用，以下说明由预设模板根据已确定的推荐结果和证据生成。” |
| LLM失败，必要信息不足 | “AI解释暂时不可用，且模板说明所需的必要信息不足，因此未生成解释。” |
| 模板自身异常 | “模板说明生成失败。推荐结果和已保存证据仍可在下方查看。” |
| 调用LLM前信息不足 | “当前推荐缺少生成说明所需的信息，未调用AI解释或模板。” |

信息缺失与模板自身失败必须区分。只要推荐本身仍满足业务准入条件，可以保留游戏名称、分数和已有证据，但不生成连贯解释段落。

### 7.9 fallback监视指标

分别记录：

- LLM实际调用次数；
- LLM有效解释成功次数；
- 传输失败次数；
- 结构／业务校验失败次数；
- fallback触发次数；
- fallback渲染成功次数；
- 因信息缺失被阻止次数；
- fallback自身渲染失败次数；
- 解释前资源不足次数。

指标口径：

```text
LLM有效解释成功率 = LLM有效解释成功次数 / LLM实际调用次数
fallback渲染成功率 = fallback渲染成功次数 / fallback实际尝试次数
解释覆盖率 = (LLM有效解释成功次数 + fallback渲染成功次数) / 需要解释的总次数
```

`fallback实际尝试次数`只统计进入模板渲染步骤的次数。`需要解释的总次数`指最终进入展示名单且按产品规则应当生成解释的推荐数量。解释前资源不足不计入LLM实际调用失败，但计入解释覆盖率的分母。原“fallback比例低于20％”不再作为当前核心质量门槛，改为后续观察指标。

## 8. 数据存储

```text
data/store/
  profiles/<profile_id>.json
  profiles/_history/<profile_id>.r0001.json
  catalog/<appid>.json
  runs/<run_id>.json
  requests/<request_id>.json
  reports/catalog-batch-<timestamp>.json

data/raw/<appid>/
  appdetails.json
  reviews.json
  tags.json              # 可选增强，不是V1.2核心依赖
```

所有正式记录使用统一信封：

```json
{
  "schema_version": "1.2",
  "kind": "profiles",
  "id": "p-1a2b3c4d",
  "revision": 2,
  "created_at": "...",
  "updated_at": "...",
  "data": {}
}
```

写入使用临时文件加`os.replace`原子替换；画像更新使用`expected_revision`乐观锁；推荐运行写入后不可修改；推荐结果直接内嵌证据句，确保目录后来变化时历史仍能原样回看。

`requests/<request_id>.json`同时保存规范化请求哈希：

- 相同`request_id`和相同哈希：返回原运行；
- 相同`request_id`但哈希不同：HTTP 409；
- 不覆盖旧运行，不重复执行付费调用。

规范化和哈希规则固定为：

```text
canonical_request = canonical JSON(
  request body excluding request_id,
  UTF-8,
  object keys sorted,
  explicit default values included,
  strings normalized according to field rules,
  no insignificant whitespace
)

request_hash = SHA-256(canonical_request)
```

同一个`request_id`永久代表第一次执行。即使画像后来更新，重复提交相同`request_id`仍返回第一次结果；需要基于新画像生成结果时必须使用新的`request_id`。`request_id`的首次认领必须使用原子创建或进程内锁，避免两个并发请求同时触发付费调用。

画像额外保存Steam同意状态、游戏参与／排除控制和融合贡献，使用户撤销后可以重新计算纯问卷画像。

存储不可用时应返回结构化错误并记录脱敏日志，不假设error run总能成功落盘。

### 8.1 V1.1到V1.2的数据兼容策略

V1.2改变了Profile、Evidence、RecommendationRun、ExplanationFacts、请求幂等索引和错误状态契约。项目尚处于开发阶段，因此不隐式读取旧schema并猜测缺失字段：

- V1.2不承诺自动迁移开发阶段的1.0/1.1 `data/store`记录；
- 升级时先备份旧目录，再清空开发store并重建fixture和真实目录；
- `data/raw`原始快照可以保留，但必须用V1.2规范重新生成catalog记录；
- 测试fixture全部升级到schema 1.2；
- 如果组内必须保留旧画像，则单独编写显式迁移脚本，并为每一种记录提供迁移前后契约测试；
- 读取到旧schema且没有迁移器时返回`schema_version_unsupported`，不得静默补默认值。

### 统一错误结构

```json
{
  "ok": false,
  "code": "invalid_input",
  "message": "request body is malformed",
  "http_status": 400,
  "retryable": false,
  "error_id": "err-...",
  "details": {"problems": []}
}
```

关键状态码：输入错误400、资源不存在404、请求或版本冲突409、上游失败502、限流429。业务上的“没有合适推荐”不是服务器错误，应返回正常的`RecommendationRun(status="no_match")`。

普通HTTP响应不暴露堆栈。详细模块、操作、文件位置和脱敏堆栈通过本地开发者模式或诊断日志查看。

## 10. 错误处理、重试、可观察性与开发者模式

- 只有超时、连接错误、HTTP 429和5xx等可恢复错误进入有限重试；
- 参数错误、私有Steam资料、模型结构持续不合法等错误不无限重试；
- 未经用户同意不得调用Steam游戏库接口；
- Steam库导入失败降级为纯问卷画像；
- 推荐解释失败先检查最低资源，再决定模板fallback或信息不足；
- 每次模板fallback都必须明确告知用户；
- 单款目录处理失败不得中断整批；
- 目录失败不得覆盖已有verified版本；
- 每次推荐保存固定顺序trace：`validate`、`route`、`hard_filters`、`score`、`decide`、`build_explanation_facts`、`llm_explain`、`fallback`、`save`；
- 每个trace记录状态、耗时、错误代码和必要的脱敏上下文；
- 所有日志和证据包不得包含API Key，SteamID使用测试账号或脱敏；
- 开发者模式也不能关闭密钥和个人信息脱敏。

### 10.1 统一诊断字段

每次错误尽量记录：

```text
error_id / request_id / run_id
workflow / module / operation
appid / profile_id
error_code / sanitized_message
retryable / attempts / upstream_status
fallback_status / fallback_missing_fields
artifact_paths / sanitized_traceback
```

### 10.2 Gradio开发者模式（P1/P2）

设置区提供“开发者模式”复选框。开启后出现：

- “执行轨迹”折叠面板；
- “错误诊断”折叠面板；
- 缺失资源及状态表；
- 相关文件位置；
- 可复制或导出的脱敏诊断信息。

普通模式仍只显示简洁、可理解的错误和fallback提示。

### 10.3 必须区分的故障位置

| 现象 | 优先检查位置 |
|---|---|
| LLM超时，模板成功 | 模型服务、网络或重试策略 |
| LLM返回非法JSON，模板成功 | 模型输出、解析或结构校验 |
| 匹配基因为空 | 匹配规则、画像或证据门槛 |
| 证据存在但未验证 | 目录引文与证据流水线 |
| fallback信息缺失 | ExplanationFacts构建或上游数据 |
| 模板文件不存在 | 配置或部署 |
| 模板字段渲染异常 | 模板代码或数据契约 |
| error run无法保存 | JSONStore或文件系统 |

## 11. 六项课程要求映射

| 标准路线要求 | V1.2等价实现 | 实际生效证据 |
|---|---|---|
| Custom Webhook | FastAPI POST端点 | 请求JSON进入Pydantic模型并触发工作流 |
| Router | 推荐mode分支、过滤分支和结果状态分支 | `trace[].branch`、`filter_drops`、`status` |
| Data Store | 版本化JSON存储 | profiles/catalog/runs/requests文件和revision |
| Error Handler | 结构化异常、有限重试、资源门控fallback和开发者诊断 | 强制故障后的warning、fallback、missing-data或error记录 |
| OpenRouter | Another Tool路线必须提供等价的模型调用组件；V1.2默认通过OpenRouter实现 | 游戏genes或解释被真实模型输出改变并保存；也可通过统一适配器替换提供商 |
| Three Scenarios | 画像、目录、推荐三个独立工作流 | 通过appid、profile_id、run_id交换已保存数据 |

六项要求不是只写在文档中：每一项都必须在测试中实际执行并改变工作流结果。课程要求的是与标准路线六个部件逐项匹配；Another Tool路线不强制使用OpenRouter品牌，但不能省略等价的语言模型调用能力。

## 12. 测试方案

### 12.1 三层测试

1. **框架单元测试**：契约、问卷映射、存储、评分、匹配基因、双轨算法、LLM适配、fallback资源检查和API；
2. **开发验收测试**：数据侧和推荐侧验收；P0覆盖Steam授权、结构化诊断和两阶段导入，P1覆盖隐私清理、请求冲突和开发者模式；
3. **实网测试**：真实Steam和默认真实模型，标记为`live`，不在普通CI中运行。

### 12.2 课程五项测试

| 测试 | 输入 | 预期结果 |
|---|---|---|
| 正常输入 | 固定、可复现的问卷答案画像＋`mode=both`＋真实演示目录 | 两条轨道返回结果，运行落盘，每条含证据；其他合法画像允许单轨为空 |
| 非法输入 | 漏答、空昵称、未同意却要求Steam导入或`top_k=99` | HTTP 400；不应发生的Steam／LLM调用为0；无新文件 |
| 无匹配路径 | `mode=surprise_me` | `status=no_match`；trace为`no_matching_path` |
| 强制错误 | 模型连接失败、非法JSON、Steam失败、目录JSON损坏或存储失败 | 触发有限重试、warning、资源门控fallback、FAILED或结构化HTTP错误，旧数据不损坏 |
| 后续读取 | 服务重启后GET旧`run_id` | 返回与生成时完全一致的运行和证据 |

### 12.3 fallback专项测试

1. LLM非法JSON且资源完整：使用模板，明确告知用户，名单和分数不变；
2. ExplanationFacts在调用前不完整：`not_attempted + insufficient_data`，不调用LLM，不计为模型调用失败；
3. 如果跨进程反序列化后的副本缺失必要字段：`blocked_missing_data`，不得强行渲染；
4. 模板文件缺失或渲染异常：`render_failed`，与信息缺失区分；
5. 价格等可选资源缺失：省略可选句子，不阻塞必要解释；
6. 标注模型失败：不得使用模板生成基因；
7. 结构化诊断JSON不得包含API Key；如果实现开发者模式，其界面同样不得包含密钥。

### 12.4 Steam授权与数据控制测试

- **P0**：未勾选同意时，游戏库接口调用为0；
- **P0**：预览请求不修改画像，只有确认提交才产生新revision；
- **P0**：Steam导入失败时纯问卷推荐仍可运行；
- **P1**：导入后可以取消某款游戏的画像参与；
- **P1**：推荐排除与画像参与可以分别设置；
- **P1**：删除所选记录只影响本地数据，不修改Steam线上游戏库；
- **P1**：完整清除后，当前画像恢复为问卷结果，历史和缓存中的个人Steam数据也被清除或脱敏。

### 12.5 V1.2新增算法与契约测试

- 用户熟悉标签远少于游戏genres时，覆盖率按用户权重计算，不受游戏额外genres数量稀释；
- 缺少genres的游戏记录`missing_surface_labels`，不会被自动划为其他轨；
- 一条用户评测只能形成C级候选证据，两条独立一致评测才可形成B级；
- 引文匹配失败时结果为Rejected，不得降为C级；
- 等级0没有明确否定证据时必须为`null`；
- 用户设置硬过滤且字段未知时按fail-closed处理，并记录具体drop reason；
- 读取旧schema且没有迁移器时返回`schema_version_unsupported`；
- 相同`request_id`和相同规范化请求返回原结果，不同请求返回409且不调用模型。

|---|---|---|
| Steam接口变化、限流或页面差异 | 采集失败或字段缺失 | 核心来源最小化、统一客户端、限速、快照、字段级部分成功和有限重试 |
| 用户未授权或资料私有 | 无法导入游戏库 | 授权前不调用；私有或失败时降级纯问卷 |
| 用户撤销Steam数据 | 当前画像、历史版本或缓存残留个人数据 | 基于问卷重算，并按隐私清理语义删除或不可逆脱敏历史与缓存中的Steam字段 |
| LLM编造引文 | 推荐理由不可信 | 引文必须在缓存原文核验，失败置为unknown |
| 引文存在但不支持评分 | verified被过度理解 | 明确verified语义，人工检查维度和分数支持关系 |
| 问卷映射不一致 | 用户画像错误 | 公开映射表、固定九维基线和逐题单元测试 |
| 高低匹配被遗漏 | 推荐偏向高强度游戏 | 使用匹配基因，支持共同规避点和强度相容 |
| closest-only绕过证据 | 弱证据内容被当成推荐 | 只允许证据合格候选进入closest-only |
| LLM JSON不合法 | 标注或解释失败 | Pydantic校验、有限重试、unknown／partial／failed或资源门控fallback |
| fallback数据不完整 | 模板生成不可靠解释 | 调用前验证并冻结ExplanationFacts；跨进程反序列化时再校验副本 |
| fallback被静默使用 | 用户误解解释来源 | 每次明确提示，开发者模式记录原因 |
| 模型或额度不可用 | 实时解释失败 | 真实目录缓存、模板fallback和诊断；不依赖模型决定推荐 |
| 核心genres来源不稳定或映射不全 | 双轨划分失真 | V1.2只依赖appdetails genres，固定taxonomy与别名表，可选标签增强不影响核心结果 |
| 30款目录类型过于集中 | 双轨演示困难 | 人工检查种子多样性，使用固定可复现测试画像，允许其他画像单轨为空 |
| JSON并发写入 | 数据冲突 | V1.2限制单机单进程；原子写入和revision冲突检查 |
| 相同request_id携带不同内容 | 错误返回旧结果 | 保存请求哈希，不一致时返回409 |
| 存储本身故障 | error run也无法保存 | 返回结构化HTTP错误和脱敏日志，不作落盘保证 |
| 开发者诊断泄露敏感信息 | 密钥或隐私泄露 | 默认关闭、仅限本地、所有输出持续脱敏 |
| V1-Final扩容成本超出 | 无法按期达到300/200目标 | 先评估30款通过率和成本，分批扩展；时间不足时优先冻结至少100款高质量真实目录，不降低标准 |

## 16. V1.2最终决策摘要

1. 保留原V1架构，不重新搭建第二套系统；
2. V1-MVP以至少30款真实游戏完成可演示闭环；V1-Final种子池约300款并以至少200款`verified`为目标，时间不足时优先保证100款高质量目录；
3. FastAPI是Custom Webhook的正式替代，Gradio负责交互与Steam数据控制；结构化诊断JSON属于P0，完整开发者诊断界面属于P1/P2；
4. 九维基因和0—4等级保持原V1方向，问卷必须具有公开、可测试的确定映射；
5. 引文原文匹配只证明可追溯，verified只表示目录准入，不等于评分客观正确；
6. 推荐判断全部由确定性规则完成；
7. 正式采用匹配基因，支持共同吸引点、共同规避点和强度相容；
8. closest-only只用于证据合格但匹配不足的候选；
9. 表层轨道使用固定的canonical genre taxonomy和用户熟悉类型覆盖率，允许合法画像单轨为空；
10. 保留Steam导入和画像融合，但必须经过用户同意并采用预览、确认两阶段接口；逐游戏控制和完整隐私清理UI按P1推进；
11. Another Tool路线必须提供等价模型调用组件；V1.2选择OpenRouter作为默认实现，并先完成单模型5款试验；
12. LLM只负责标注和解释，模板不得生成基因或证据；
13. fallback必须经过最低资源检查，每次使用都明确告知用户；
14. fallback信息缺失、模板自身失败和LLM失败分别记录，不使用单一fallback率代替全部质量判断；
15. P0输出模块级结构化诊断和执行轨迹；P1/P2可增加本地开发者模式界面，同时持续脱敏；
16. 相同request_id但请求内容不同返回409；价格保存币种、地区和时间；存储故障不承诺error run落盘；
17. A/B/C/Rejected证据等级具有确定语义，引文匹配失败必须Rejected；等级0同样需要明确证据；
18. V1.2不静默兼容旧schema；开发数据通过备份后重建，必要时另写显式迁移脚本；
19. 面向全Steam的运行时动态候选发现、多模型比较和更大规模持续更新列入后续工作；
20. 最终交付必须包含五项测试的真实执行证据，而不只是页面截图或HTTP 200。
